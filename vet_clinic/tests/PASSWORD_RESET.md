Password reset uses `POST api/mobile/v1/password_reset.php`:

- Request: `{ "action": "request", "email": "client@example.com" }`
- Complete: `{ "action": "reset", "email": "client@example.com", "otp": "123456", "password": "NewPassword123!", "confirmPassword": "NewPassword123!" }`

Only active, verified clients can reset. Requests are queued for admin review without generating or emailing an OTP. Admins review them in the Password reset requests section on the Users or Client Accounts page. Approve & send OTP generates the code and records the reviewer; Reject sends nothing. Failed email delivery leaves the request pending for retry. Review forms require an admin session and a valid CSRF token; the service also checks the reviewer's role. The public API accepts only request/reset, never review actions.

Account-activation OTPs are separate. Reset codes expire 10 minutes after admin approval, are hashed, and are consumed atomically with the password change and mobile session revocation. A new OTP request needs fresh approval and invalidates the previous approval. Repeated pending requests do not create duplicates. Stale or duplicate admin submissions cannot approve a replaced request. Each account can receive five codes per hour with a 60-second cooldown; ten failed guesses block further guesses and sends for the remaining hour. Responses do not disclose whether an email belongs to an eligible account. Clients can return using Already approved? Enter your OTP without submitting another request.

Deploy the mobile endpoint, `includes/mobile_password_reset.php`, `includes/admin_password_reset_requests.php`, `admin/password_reset_review.php`, the updated Users/Client Accounts pages, and both `migrations/mobile_password_resets.sql` and `migrations/mobile_password_reset_requests.sql` together with the mobile app changes. Tables are created when permitted; otherwise apply both migrations first. The second migration also upgrades installations that already have the original reset table. The endpoint uses the existing mobile token schema.

Email must be enabled using the existing `config/mail.local.example.php` template copied to ignored `config/mail.local.php`, or the environment settings documented in `config/mail.php`. Set real email sending to true and supply the clinic's SMTP configuration locally. Never commit SMTP credentials. Requests can be queued without SMTP, but admin approval displays an error and keeps the request pending if real sending is disabled or fails. An SMTP acceptance is not a guarantee of inbox delivery; verify receipt with a clinic-controlled test mailbox.

Run `C:/xampp/php/php.exe vet_clinic/tests/mobile_password_reset_test.php` from the workspace root. It creates and removes a randomly named test database, uses synthetic accounts and a fake mail transport, and never changes clinic passwords or sends real email. It covers the approval gate, reviewer authorization, duplicate and stale requests, rejection, expiry, guessing limits, resend cooldown and invalidation, eligibility, replay, password replacement, token revocation, and rollback on mail failure. Run `npm run lint` and `npx expo export --platform web` from the mobile project for client checks.
